# 需求分析、需求拆分、交互原型與測試設計

## 基本原則

- 全程使用中文輸出。
- 嚴格按照「需求 → 需求拆分 → 交互原型 → 使用者確認 → 測試用例」的順序執行。
- 不臆測關鍵業務規則；資訊不足時列出待確認問題，並明確標示暫時採用的假設。
- 所有產出使用统一編號，確保需求、任務與測試用例可以互相追蹤。
- 本流程生成的 Markdown 文件統一放在 `docs/` 文件夾，包括 `docs/requirements.md`、`docs/breakdown.md`、`docs/timeline.md` 和 `docs/test-cases.md`；不得在倉庫根目錄另建同名流程文件。`AGENTS.md`、`README.md` 及技能說明文件不屬於流程產物，不因此移動。
- 每個流程步驟的開始、完成、暫停、重新開啟及使用者確認，均須即時記錄於 `docs/timeline.md`；時間綫獨立維護，不得寫入 `AGENTS.md`。
- 原型未經使用者明確確認，不得進入測試用例階段。

## 1. 輸出需求

先分析使用者提供的內容，輸出 `docs/requirements.md`，至少包含：

1. **背景與目標**：要解決的問題、目標使用者及預期價值。
2. **範圍**：本期包含與不包含的功能。
3. **使用者角色**：各角色的權限與主要操作。
4. **功能需求**：以 `REQ-001`、`REQ-002` 等編號逐項描述，包含觸發條件、主要流程、業務規則及異常流程。
5. **資料與介面**：重要欄位、資料規則，以及已知的外部系統或介面依賴。
6. **非功能需求**：效能、安全性、相容性、可用性等要求；未提及時標示為待確認，不自行添加硬性指標。
7. **驗收標準**：每項核心需求均須提供可判斷通過或不通過的標準。
8. **約束、依賴與待確認事項**：集中列出假設、風險及需要使用者補充的資訊。

需求描述應具體、無歧義，避免只寫「支援」「優化」等無法驗收的字句。

## 2. 需求拆分與小時估算

根據已確認的需求輸出 `docs/breakdown.md`。將工作拆分為可獨立執行、可驗收的任務，並遵守：

- 必須按功能點逐層細分，不得只按頁面、模組或前後端技術工作粗略拆分。每個功能點應繼續拆到使用者可感知、可獨立驗收的最細交互行為，例如點擊按鈕、提交表單、關閉彈窗、切換頁籤、翻頁或拖動標記。
- 每個最細交互任務均須明確操作入口或觸發條件、系統回饋，以及成功、失敗或異常結果；不得使用「完成某功能」「實現某頁面」等無法直接驗收交互的表述代替拆分。
- 例如「課堂翻頁」不得只列為一項籠統任務，應至少細分為「教師點擊下一頁按鈕」「教師點擊上一頁按鈕」「學生端同步顯示當前頁」「斷線重連後恢復當前頁」等具體交互。
- 使用 `TASK-001`、`TASK-002` 等編號，每項任務關聯對應的需求編號。
- 工時一律以小時表示，可使用 0.5 小時為最小單位，不得只提供人天或人週。
- 單項任務若超過 8 小時，繼續拆分；若無法合理拆分，說明原因。
- 估算須包含完成該任務所需的設計、開發、自測與調整，避免漏項或重複計算。
- 標示前置依賴與主要交付物，不確定之處列入估算假設。

任務明細使用以下欄位：

| 任務編號 | 關聯需求 | 任務內容 | 交付物／完成標準 | 前置依賴 | 預估工時（小時） |
|---|---|---|---|---|---:|

表格後提供：

- 各模組工時小計與全部工時總計。
- 估算假設、風險及可能影響工時的因素。
- 如需另列緩衝工時，與任務工時分開呈現，不得隱含在任務估算中。

## 3. 輸出可交互原型

根據已確認的需求製作可交互原型，可使用 Figma 等外部原型或設計網站，也可製作本地 `prototype.html`。依可用工具與使用者偏好選擇合適形式；使用本地 HTML 時，以內嵌 HTML、CSS 與 JavaScript 實作，確保可直接在瀏覽器開啟。

原型要求：

- 覆蓋核心頁面、主要操作流程及需求中明確要求的狀態。
- 提供可實際操作的導覽、按鈕、表單、頁籤、彈窗等元件，而非只有靜態圖片。
- 點擊或提交後應有明確回饋；使用模擬資料時須清楚標示。
- 視需求補上空白、載入、錯誤、成功及無權限等狀態。
- 保持版面與操作流程一致，並標示原型尚未實作的邊界。
- 附上頁面或流程與需求編號的對照，方便使用者逐項檢查。
- 使用 Figma 等外部網站時，提供可直接開啟並進入原型檢視或演示模式的完整連結，而非只提供網站首頁。
- 外部連結須設定適當的檢視權限；若仍需登入或申請權限，必須事先明確說明。
- 不得提供未實際建立、未驗證或無法存取的原型連結。
- 交付前實際檢查連結或檔案可開啟，主要按鈕、導覽及核心流程可以操作。

完成後提供原型連結或檔案位置、操作說明及存取條件，明確請使用者檢查：

> 請透過以上連結或檔案檢查原型是否符合需求，尤其確認頁面範圍、操作流程、欄位與業務規則。請回覆需要修改之處，或明確確認原型通過。

若使用者提出修改，先同步更新需求、拆分與原型，再次提供更新後的連結或檔案請其檢查。只有收到明確確認後，才繼續下一階段。

## 4. 根據拆分結果輸出測試用例

依據需求、驗收標準、已確認原型及 `docs/breakdown.md` 輸出 `docs/test-cases.md`，使用 `TC-001`、`TC-002` 等編號。每項核心需求與拆分任務都應有對應驗證，不只測試正常流程。

測試範圍應依實際需求涵蓋：

- 正常流程與各角色權限。
- 必填、格式、邊界值及重複操作。
- 異常輸入、失敗處理與恢復流程。
- 頁面狀態、資料變更及跨模組影響。
- 需求中明確要求的相容性、效能與安全性。

測試用例使用以下欄位：

| 用例編號 | 關聯需求／任務 | 用例標題 | 優先級 | 前置條件 | 測試資料 | 操作步驟 | 預期結果 |
|---|---|---|---|---|---|---|---|

編寫要求：

- 操作步驟按順序編號，預期結果必須具體且可觀察。
- 一個用例聚焦一個驗證目標，不把多個無關場景合併。
- 優先級統一使用 P0、P1、P2，並在文件中說明分級依據。
- 最後檢查追蹤關係：`REQ → TASK → TC`；若存在未覆蓋項目，列出原因與待確認事項。

## 交付檢查

交付前確認：

- 四項產出內容一致，沒有原型已修改但需求或測試未同步的情況。
- 原型已由使用者明確確認。
- 工時全部以小時呈現，且小計、總計計算正確。
- 核心需求、拆分任務及測試用例均可透過編號互相追蹤。
- 所有假設、待確認事項及未覆蓋範圍均已清楚列出。
